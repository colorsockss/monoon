# KeyRoom 스크립트 필드 이름 변경 검증

KeyRoom에서 같은 `MovementPlayer.prefab`을 두 번 배치했다. 위쪽 플레이어는 프리팹 원본의 속도 240을 상속하고 아래쪽 플레이어는 속도를 320으로 덮어쓴다. **F3**으로 비교 씬을 열고 방향키나 WASD로 둘을 함께 움직일 수 있다. [사용법](../../../../docs/manual/scripting.md#inspector-필드-이름-바꾸기) · [회귀 검사 재현 방법](../../KeyRoom.FieldRename/README.md)

## 저장 후 다시 열기

검증용 사본의 `PlayerMovement` 초기값을 177로 두었다. 저장된 240 대신 C# 초기값을 쓰면 검사에서 차이가 드러난다. 배포 샘플의 초기값은 240이다.

1. 배포 에디터의 프리팹 Inspector와 씬 Inspector에서 이전 필드 **Speed**를 읽고 씬을 저장했다.
2. 에디터를 열어 둔 채 선언을 **MoveSpeed**로 바꾸고 `[FormerlySerializedAs("Speed")]`를 붙였다. 해당 필드를 읽는 다른 C# 스크립트도 변경했다. 프리팹 원본부터 저장한 뒤 이전 이름이 남은 씬을 읽었다.
3. 씬을 저장하고 프리팹과 씬을 다시 열었다. 상속 인스턴스에는 속도 오버라이드가 없고, 아래쪽 인스턴스에만 **MoveSpeed** 오버라이드가 하나 있는지 검사했다. 저장된 YAML에서 프리팹 원본, 인스턴스 값, 프리팹 비교 기준에 새 키가 쓰였는지도 확인했다.

## 실제 이동 거리

에디터의 **Play** 버튼으로 KeyRoom을 시작한 뒤 첫 방에서 F3을 누르고 오른쪽 방향을 15틱 유지하는 입력을 재생했다. 같은 OS에서 에디터가 저장한 프로젝트로 Release와 Native AOT를 각각 빌드했다. 독립 게임에서는 실제 배포 실행 파일이 같은 입력을 창 없이 재생했다. 검증용 스크립트는 입력을 누르고 놓을 때 두 플레이어의 월드 X좌표를 읽었다. 고정 틱은 60Hz이므로 기대 이동량은 각각 60px와 80px다.

| 환경 | 재열기 속도 (원본 / 상속 / 개별 설정) | Scene Play (px) | Release (px) | Native AOT (px) |
| --- | ---: | ---: | ---: | ---: |
| macOS arm64 | 240 / 240 / 320 | 60 / 80 | 60 / 80 | 60 / 80 |
| Windows 11 Enterprise LTSC x64 · QEMU | 240 / 240 / 320 | 60 / 80 | 60 / 80 | 60 / 80 |
| Debian 12 x64 · QEMU · Xvfb 에디터 | 240 / 240 / 320 | 60 / 80 | 60 / 80 | 60 / 80 |

거리 열은 상속 인스턴스와 개별 설정 인스턴스의 순서다. 아홉 실행의 입력과 이동 결과가 같았다. [세 에디터의 Inspector 기록](inspector.tsv) · [실행별 좌표 변화와 해시](runs.tsv)

Mac에서는 기존 Play Inspector 회귀도 새 이름으로 실행했다. 첫 방 Player의 **MoveSpeed**를 240에서 320으로 수정하고 Stop하면 240으로 돌아왔다. 선택 적용하면 320이 저장됐고 Undo 한 번으로 240이 복원됐다. [검사 방법](../../KeyRoom.PlayInspector/README.md)

## Mac 배포 게임 창

관찰 스크립트가 없는 배포 샘플도 이 Mac에서 Release와 Native AOT의 SDL 창에 F3과 오른쪽 방향키를 보내 확인했다. 처음에는 두 사각형의 왼쪽 끝이 같은 X에 있었다. 두 빌드 모두 이동 후 아래쪽 사각형이 위쪽보다 약 4/3배 멀리 갔다. 키를 실제 시간 동안 누른 창 캡처의 거리는 화면 픽셀로 측정했다. [창별 픽셀 좌표](mac-window.tsv) · [Native AOT 게임 화면](mac-native-aot.png)
