# 큰 방을 나눠 읽기

2026-11-22 · macOS 27.0.1 (26A434) · Apple M4 Max · .NET SDK 10.0.101. 같은 소스로 플레이어 템플릿, CollisionLab 개발용 Release·Native AOT 빌드, 패키징한 에디터를 만들었다. Windows·Linux 게스트 결과는 [아래](#windows-x64와-linux-x64-게스트)에 있다. [실행 방법](../../CollisionLab.SplitLoading/README.md) · [사용법](../../../../docs/manual/scene-streaming.md#큰-방을-여러-프레임에-나눠-읽기)

측정한 방은 CollisionLab의 충돌체 1만 개 방에 4096×4096 배경 PNG 네 장을 더한 방이다. 실험실 방에는 스프라이트 세 개가 상주한다. 방이 연결되면 상주 파일이 일곱 개가 된다. 예산 0은 이전 방식이다. 준비를 시작한 업데이트에서 오브젝트를 모두 만들고, 업데이트마다 파일 하나를 게임 스레드에서 디코딩·업로드한다. 예산 4 ms는 오브젝트 생성과 업로드에 업데이트당 4 ms를 쓰고, PNG는 워커 스레드에서 디코딩한다.

## 개발용 게임 헤드리스 재생

SDL 소프트웨어 렌더러에 텍스처를 올리고, 프레임 사이를 1/60초에 맞춰 기다렸다. 업로드는 GPU 전송이 아니라 메모리 복사다. 프레임 시간은 기다린 시간을 뺀 작업 시간이다. 구간은 키를 누른 다음 프레임부터 연결 프레임(취소하면 마지막 로딩 프레임)까지다. 전체 로딩 시간은 구간 프레임마다 1/60초와 작업 시간 중 큰 값을 더했다. 각 값은 3회 실행의 중앙값이다.

- 예산 4 ms의 가장 느린 프레임은 나누지 않는 단계다. Release 추가는 연결 프레임이다. 실험실 월드와 1만 개 방을 합쳐 다시 색인하는 Scene.Commit이 22.3–22.6 ms였다. 나머지는 오브젝트를 모두 만든 뒤 충돌·그리기 색인을 만드는 프레임이다. Scene.Instantiate가 14.4–20.3 ms였고, 이 프레임에서 Gen0 수집이 1–3회 일어났다.
- 예산 4 ms에서 배경 디코딩은 워커 스레드에서 오브젝트 생성과 겹친다. 이 때문에 구간 프레임은 늘었지만 전체 로딩 시간은 줄었다. 게임 스레드의 Scene.Upload 합계는 약 300 ms에서 9–13 ms로 줄었다.

업로드한 배경 수는 그 실행의 Scene.Upload 합계에서 계산했다. 예산 0에서는 한 장에 약 77 ms, 4 ms에서는 약 3–4 ms다. Native AOT 4 ms 첫 실행은 19번째 프레임 취소가 늦어 방이 연결됐다. 그래서 17번째 프레임으로 다시 실행했다. 다른 실행은 첫 시도에서 취소됐다. 취소한 실행에서는 방이 연결되지 않았다.

## 에디터 Scene Play

SDL Scene 패널에서 **4**로 방을 추가했다. 로딩 구간은 연결 프레임 직전까지다. 연결 프레임은 따로 적었다. 3회 실행의 중앙값이다.

| 예산 | 구간 프레임 | 최장 프레임 | p95 프레임 | 구간 시간 합계 | 연결 프레임 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 24 | 118.139 ms | 104.951 ms | 828.431 ms | 5,387.196 ms |
| 4 ms | 37 | 72.403 ms | 23.940 ms | 757.911 ms | 5,466.067 ms |

- 실행별 최장 프레임은 예산 0이 118.1 / 118.1 / 119.0 ms, 4 ms가 73.6 / 72.4 / 70.3 ms였다. 예산 0에서는 오브젝트 1만 개를 한 번에 만든 프레임(Scene.Loading 101–102 ms)이 가장 길었다. 4 ms에서는 색인을 만든 프레임(Scene.Instantiate 46.6–50.8 ms, Gen0 1회)이 가장 길었다. 헤드리스 Release(14–20 ms)보다 긴 이유는 측정하지 않았다. 에디터는 `DOTNET_TieredCompilation=0`을 적용하지 않는다.
- 연결 프레임 5.1–5.6초는 두 예산에서 같았다. 이 중 Scene.Commit은 30–36 ms였다. Play Hierarchy를 다시 만드는 Editor 샘플이 0.63–0.92초, 어느 샘플에도 속하지 않은 시간이 4.3–4.9초였다. UI 스레드 할당은 매번 6.35 GB였다. roadmap 10.3에서 Field10000을 열 때 기록된 5.5초와 6.4 GB는 이 에디터 Hierarchy 갱신 비용이다. 씬 로딩 경로에 속하지 않아 이번에 고치지 않았다.
- 실험실 방을 다시 연 뒤 진행도 0.55를 넘어 취소했다. 6회 모두 상주 3 · 디코딩 0 · SDL Scene 패널 텍스처 3으로 돌아왔다. 연결 직후에는 상주 7 · 텍스처 7이었다.

## 회귀 검사

`./monoon test` 전체 결과와 [`SplitLoadingChecks`](../../Engine.Checks/SplitLoadingChecks.cs)의 [12개 항목](checks.txt)은 다음을 확인한다. KeyRoom 복사본에 생성자가 0.5 ms 걸리는 스크립트 오브젝트 600개, PNG 12개, WAV 하나를 가진 방을 만든다. 시험용 자원은 업로드마다 3 ms, 디코딩마다 15 ms가 걸린다.

- 동기 `LoadScene`, 예산 0, 예산 4 ms로 교체한 결과의 오브젝트 ID·이름·부모·위치, `OnCreate` 호출, 상주 파일이 같다. 진행도는 줄지 않고 1에서 끝난다.
- 업데이트당 컴포넌트 생성은 최대 9개(카메라 1개 + 0.5 ms 생성자 8개), 3 ms 업로드는 최대 2개다. 예산 0은 오브젝트 전체를 한 업데이트에서 만들고 파일을 업데이트당 하나씩 올린다.
- 추가하는 동안 실험실 방의 틱이 매 업데이트 진행되고 플레이어가 움직인다. 디코딩은 워커 스레드에서, 업로드는 게임 스레드에서 실행된다.
- 오브젝트 생성 중과 디코딩·업로드 중에 취소하면 업로드한 파일, 디코딩한 버퍼, 추가된 오브젝트가 시작 상태로 돌아온다. 취소한 방을 다시 추가하고 제거할 수 있다.

기존 씬 전환 검사(`SceneStreamingChecks`)도 통과했다. `./monoon ci`로 InventoryLab을 Release·Native AOT 배포용으로 다시 빌드했고 `./monoon test replay`를 통과했다. 입력 재생 저장 파일의 SHA-256은 기존 기록과 같은 `EED41DEF…E70F795`였다. 두 배포본에 SkiaSharp, Avalonia, 에디터·빌드 도구 어셈블리가 없었다.

## Windows x64와 Linux x64 게스트

2026-11-23, 이 Mac의 QEMU(TCG) 게스트에서 Mac에서 `prepare`로 만든 같은 사본을 각 게스트에서 개발용 Release와 Native AOT로 빌드했다. 모든 시간은 에뮬레이션 값이며 Mac과 비교하지 않는다. [게스트 환경과 실행 방법](../x64-guest-10.2-10.8/README.md)

### 헤드리스 재생: 원래 검사(300프레임, 3회)는 네 배포본 모두 실패

| 게스트 | 배포본 | 결과 | 첫 실패 |
| --- | --- | --- | --- |
| Windows 11 x64 | Release | **실패** | 1회차 예산 0 취소. 230·228·226번째 프레임 시도 모두 취소 전에 방이 연결됨 |
| Windows 11 x64 | Native AOT | **실패** | 2회차 예산 0 취소. 196·194·192번째 프레임 시도 모두 연결됨. 1회차의 4 ms 추가·교체는 298프레임 안에 연결되지 않음 |
| Debian 12 x64 | Release | **실패** | 3회 모두 진행. 4 ms 추가·교체 6번 모두 298프레임 안에 연결되지 않아 `a add load did not finish within 300 frames` |
| Debian 12 x64 | Native AOT | **실패** | 1회차 예산 0 취소. 161·159·157번째 프레임 시도 모두 연결됨 |

- 에뮬레이션에서는 키를 누른 뒤 첫 업로드까지 약 170프레임(약 3초)이 걸렸다. 1/60초 간격으로 진행하는 재생에서 예산 0 로딩은 150–250프레임(macOS 14프레임), 예산 4 ms 로딩은 400–640프레임이 걸렸다. 그래서 4 ms 로딩은 300프레임짜리 기록 안에 끝나지 않았다. 이때 검사기는 업로드가 없으므로 마지막 프레임 직전에 Backspace를 넣는다. 따라서 그 “취소”는 취소 경로를 검사하지 못한다.
- 예산 0 취소는 같은 입력이라도 실행마다 연결 프레임이 10프레임 이상 달랐다. 검사기는 2프레임씩 세 번 앞당겨 다시 시도하므로 위 세 실행에서 취소 시점을 찾지 못했다. 취소가 연결 전에 들어간 예산 0 실행(Linux Release 3회, Windows Native AOT 1회차)은 모두 상주 3 · 디코딩 0 · SDL 텍스처 3으로 돌아왔다.
- 검사기의 Release 대 4 ms 최장 프레임 비교까지는 도달하지 못했다. 저장소의 검사기는 바꾸지 않았다.
